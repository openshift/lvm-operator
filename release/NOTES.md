# Konflux onboarding notes for release-4.12 (RHEL8)

This directory is a backport of the Konflux build scaffolding from `release-4.14`,
adapted for the RHEL8-based 4.12 stream. It was authored as part of onboarding
LVMS 4.12 to Konflux so that Z-stream updates can be released through it.

## Why this is not a straight copy of release-4.14

LVMS 4.12 and 4.13 are **RHEL8**-based; 4.14 and later are **RHEL9**-based. This
was verified against the published images:

| image                                 | 4.12 | 4.14 |
|---------------------------------------|------|------|
| `lvms4/lvms-rhel8-operator`           | yes  | no   |
| `lvms4/lvms-rhel9-operator`           | no   | yes  |
| `lvms4/lvms-must-gather-rhel8`        | yes  | no   |
| `lvms4/lvms-must-gather-rhel9`        | no   | yes  |
| `lvms4/topolvm-rhel8`                 | yes  | no   |
| `lvms4/topolvm-rhel9`                 | no   | yes  |
| `lvms4/lvms-operator-bundle`          | yes  | yes  |

Consequences, all reflected in this directory:

* Base images are UBI8 / `openshift-golang-builder:rhel_8_1.20` (4.12 is `go 1.20`).
* Image `name` labels use the `-rhel8` repositories and the `cpe` labels end in `::el8`.
* The RPM lockfile inputs (`rpms.in.yaml`) point at the `rhel-8-*` CDN repos.
* `release-4.12` still vendors its dependencies, so `release/operator/konflux.Dockerfile`
  copies `vendor/` and builds with `-mod=vendor`. 4.14 dropped `vendor/` and uses
  `-mod=readonly`.
* On 4.12 the CSI snapshotter ships as `ose-csi-external-snapshotter-rhel8`, not the
  unsuffixed `ose-csi-external-snapshotter` used from 4.14 onward.

## TODO before the first Konflux build: generate `rpms.lock.yaml`

**`release/operator/rpms.lock.yaml` and `release/must-gather/rpms.lock.yaml` are
intentionally NOT included in this change.**

They are architecture- and content-specific lockfiles that must be resolved against
the **el8** CDN repositories. Generating them requires Red Hat Subscription Manager
credentials and a `registry.redhat.io` pull secret, which were not available to the
automation that produced this backport. Committing lockfiles resolved against el9
content — or hand-written ones — would produce an unbuildable or, worse, a silently
wrong image.

The LVMS team must generate them from a subscribed host:

```bash
export RHSM_ORG="<YOUR_RHSM_ORG>"
export RHSM_ACTIVATION_KEY="<YOUR_RHSM_ACTIVATION_KEY>"
export AUTH_FILE="/path/to/your/docker/config.json"

# From the lvm-operator repo root, on the release-4.12 branch
make -f release/konflux.make rpm-lock TARGET=operator
make -f release/konflux.make rpm-lock TARGET=must-gather
```

See `release/hack/generate-rpm-lock.md` for the full prerequisites.

Until both lockfiles exist, the `prefetch-input` RPM step in
`.tekton/lvm-operator-push.yaml` and `.tekton/lvms-must-gather-push.yaml` will fail.

### Also confirm before generating

The `arches:` list in both `rpms.in.yaml` files was carried over from 4.14
(`aarch64`, `x86_64`, `s390x`, `ppc64le`). It was **not** possible to verify from
this environment which architectures LVMS 4.12 actually shipped, because the
registry mirror used for inspection down-converts manifest lists to single-arch
schema-v1 manifests. Please confirm the 4.12 arch set and trim the list (and the
`build-platforms` in `.tekton/lvm-operator-catalog-push.yaml`) if 4.12 is not
built for all four.

## TODO: generate the FBC catalog templates

`release/catalog/lvm-operator-catalog-template.yaml` and
`lvm-operator-catalog-candidate-template.yaml` are **not** included either. Both are
marked `# WARNING THIS FILE IS AUTOGENERATED - DO NOT EDIT` on 4.14 and are produced
by `release/hack/generate_catalog_template.sh`, which enumerates published bundle
tags and pins them by digest using authenticated `skopeo` calls against
`registry.redhat.io` and `registry.stage.redhat.io`.

Generate them with:

```bash
make -f release/konflux.make catalog-template Y_STREAM=v4.12
```

For reference, at the time of writing the published 4.12 bundles were
`v4.12.0` through `v4.12.9` (latest `v4.12.9`, built 2025-01-17), carrying
channel `stable-4.12`, and the floating `v4.12` y-stream tag exists — so the
generator will discover the stream correctly.

## Pinned digests in `bundle/bundle.konflux.Dockerfile`

The `ARG` digests were taken from the `relatedImages` stanza of the published
`lvms-operator-bundle:v4.12.9` ClusterServiceVersion, which records true
`registry.redhat.io` digests. They represent the 4.12.9 content set and will be
kept current by Mintmaker/Renovate once the components are onboarded.

## Makefile change

`bundle` was split into `bundle` and `bundle-base`, mirroring the same split on
`release-4.14`. `render_templates.sh` calls `bundle-base` so the Konflux bundle
build does not need the jsonnet toolchain (fetched with `@latest`, therefore not
hermetic). `OPERATOR_VERSION ?= $(VERSION)` was added so existing `make bundle`
invocations keep their previous behaviour.
